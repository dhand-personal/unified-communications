# Unified Communication

## What this skill is for

Sales communication is scattered by default: a thread in Gmail, a call transcript in Gong, notes in OneNote, a text exchange that lives nowhere searchable. This skill exists to make that history queryable as a single account/person/topic view, and to be honest about which sources it's actually pulling from at any given moment rather than quietly answering from whatever happens to be easiest.

Two things matter more than anything else here:

1. **Prefer full transcripts over summaries wherever the underlying source allows it.** A summary is someone else's compression of what was said, and it can miss the detail someone actually needs. Check `references/catalog.md` for what each source's connector actually gives you before treating it as "done."
   - **Default to whatever MCP connector is already present for a source.** It needs no separate credential setup, so it's the simplest path and the right first choice. Only build or use a direct API integration when there's no MCP for that source, or the person specifically asks for the API path — never build one unprompted just because it might be more thorough.
   - Some MCP servers bundle several tools, some full-content and some summary-only. "Default to MCP" means use the MCP tool that actually gives full content when that's what's needed, not whichever tool happens to be called first. If the connected MCP genuinely has no full-content option for something (only summary/metadata tools), say so plainly when answering rather than quietly settling — but that's a fact to report, not a reason to go build an API integration on your own initiative.
   - Gong is the one confirmed exception worth knowing by name: its MCP server is structurally incapable of returning a raw transcript through any tool it offers (confirmed straight from Gong's own docs — see `references/catalog.md`). Because MCP and API genuinely give different things here (synthesized summary vs. verbatim transcript), don't silently default either way for Gong — ask the person which they want during setup, per `references/catalog.md`'s Gong entry, and say plainly if a Gong MCP result is a summary rather than presenting it as if it were the transcript.
2. **Never claim a source is active when it isn't.** This skill is meant to be shared, and the person running it may have a completely different set of tools and credentials than whoever wrote it. Its whole value depends on being truthful about what's actually wired up versus what's just listed as possible. Don't fabricate a "found nothing" result for a source that was never actually connected — say so explicitly, and offer to help connect it.

## First run: the setup interview

Before answering any real query, check whether a config file exists at `~/.unified-communication/connectors.json` (use `scripts/manage_config.py --show` to check and print it). If it doesn't exist yet, this is a first run — run a short interview before doing anything else (unless another skill triggered this with no person to interview — see "Being useful to other skills" below for that case):

1. Tell the person, briefly, what this skill does.
2. Walk through the source catalog in `references/catalog.md` and ask which of these they actually use for work communication. Don't ask about all of them in a wall of text — group them naturally (email, meetings/calls, notes, CRM, other) and let them tell you what applies. Every group is a menu, not a checklist: always leave room for something not listed ("or something else — Fathom, Chorus, a CRM's call log, whatever you actually use") and take that answer at face value rather than steering them back toward the catalog. The catalog is a list of what's common, not a limit on what's supported.
   - If they use a CRM (Salesforce, HubSpot, or otherwise) alongside anything that might sync into it, ask directly whether it auto-logs emails or calls (Einstein Activity Capture, a Gmail/Outlook connection, a dialer integration, etc.) and which sources feed into it. Record that against the CRM's config entry — see `references/catalog.md`'s "Watch for duplicates" note for why this matters and how it's used later.
3. For each source they say they use — whether or not it's in the catalog — check what's realistically available *right now* in this session/environment. "Available" means actually confirmed, not assumed: check the current session's actual tool list (or, for scripted sources, run a real lightweight check like `ping`) rather than trusting the catalog's description of what a source *usually* offers, memory of a different session, or the person's own belief that something is connected. The catalog says what a source is capable of; only the live tool list or an actual check call says what's true right now.
   - **Gong is a special case — don't apply the default-to-MCP logic below to it** (see the Gong exception under "What this skill is for" above for why). Ask the person directly which they want: MCP-based summaries, API-based full transcripts, or both. `references/catalog.md`'s Gong entry has the exact question to ask and both setup paths, including the credential walkthrough for the API path. Mark `"status"` / `"access"` per whichever path(s) they actually confirm working, same rule as everything else — never live on the strength of an intention.
   - For everything else, if an MCP connector is present and connected, that's the default: mark it `"status": "live", "access": "mcp"`. Note in the config which of its tools gives full content vs. summary/metadata, if it has more than one, so a later query knows which to call.
   - Only consider a direct API path if there's no MCP connector for this source, or the person specifically asks for API access instead of (or in addition to) the MCP. In that case, mark it `"status": "planned", "access": "api"` and briefly note what setup it would take (see `references/catalog.md` for per-source specifics; if the source isn't in the catalog yet, ask the same questions catalog.md asks of everything else — is there a documented API, does it separate a full-content endpoint from a summary/highlights one — and add a short entry so it doesn't have to be re-derived next time). For any API-based source (Gong included), never collect the actual key/secret from the person in chat — see catalog.md's credential-handling note.
   - If there's no practical MCP or API path at all (or the person just wants a manual option), mark it `"status": "live", "access": "manual"` — this is always available for pasted text regardless of anything else.
4. Write the result with `scripts/manage_config.py --init` (pass the connector list as JSON — see the script's `--help` for the exact shape).
5. Tell the person what's live now versus what's just noted for later, in one or two sentences, and proceed to answer their actual query using whatever is live.

This interview only needs to happen once. On every later invocation, read the existing config instead of re-asking.

## Adding, removing, or checking connectors later

The person doesn't need to re-run the whole interview to change one thing. Recognize requests like "add Gong to this," "stop pulling from OneNote," "what sources are you using right now," or "is Zoom set up yet" as config changes, and handle them directly with `scripts/manage_config.py` (`--add`, `--remove`, `--show`). This applies just as much to a tool that isn't in the catalog at all — "add Fathom" gets the same treatment as "add Gong," not a "that's not supported" response. When adding a source that needs API credentials, explain what's needed (again, `references/catalog.md` has the specifics per source, or work it out fresh for something new) rather than marking it live prematurely.

## Answering a query

Once the config is in place, a query like "what's the history on the Acme account" or "has pricing come up with Jane Doe in the last quarter" breaks down like this:

1. **Pull out the query parameters**: account and/or person name, topic if any, and a time window. If the person doesn't give one, default to the last 90 days — and say so in the answer ("covering the last 90 days — let me know if you want further back") rather than silently applying a window they don't know is there. If a name turns up more than one plausible match in any source — two contacts named Jane, two companies matching "Acme" — **ask which one rather than guessing**, the same rule Gong's account/deal mode already follows (see `references/gong_modes.md`) applied everywhere, not just there. Don't pick by recency or by whichever record loaded first.
2. **Check the config** for which sources are currently `"status": "live"`.
3. **Check what this conversation already has** before fanning out again. If an earlier turn in this same conversation already pulled and normalized records for this account/person that cover what's being asked now (a follow-up question a minute after the first one, say), reuse those instead of re-querying every live source from scratch. Only fetch what the new ask actually adds: a wider or different time window, a source that wasn't queried before, or an explicit request to check for anything new. This is a cheap way to avoid repeating the same fan-out for every follow-up in one sitting — it is *not* a substitute for a real cache across separate sessions (see the note at the end of this section).
4. **For each live source that still needs querying, gather results**:
   - `mcp` sources other than Gong: call the relevant MCP tool(s) directly (e.g. the Gmail connector's search/get tools) using the query parameters. This has to happen live, in this conversation turn — a standalone script can't call another tool's MCP connector on its own, so don't try to shell out for this part.
   - **Gong via `mcp`**: call `ask_account`, `ask_deal`, or `generate_brief` as fits the query, with `includeSources: true` so you can cite what it drew from. It's a synthesis, never a transcript (see the Gong exception above) — say so in the answer rather than presenting it as verbatim.
   - **Gong via `api`**: this is a scripted pull, not a live MCP call. Use `references/gong_modes.md` to decide which mode the query implies (account/deal/bulk/owner/content-search) and follow that mode's steps, calling `scripts/gong_client.py` (and `scripts/extract_gong_ids.py` if account/deal mode needs HubSpot meeting records resolved to Gong call IDs first). `references/gong_api_patterns.md` has the endpoint/auth details if something errors, and `references/gong_content_search.md` has the content-search internals. Use `scripts/format_transcript.py` only if the person wants transcripts written to files rather than synthesized inline.
   - `manual` (pasted) sources: use whatever the person has pasted into the conversation, plus anything already normalized and saved from earlier in the session (see `references/schema.md`).
   - Anything `"status": "planned"` gets skipped, but say so plainly in the final answer ("Gong isn't connected yet, so this doesn't include call transcripts") rather than silently omitting it.
   - For any source actually queried, check `references/catalog.md`'s entry for a result-time caveat (marked "flag directly in results, not just at setup" — e.g. Nooks only covering reps with an AI Coaching seat, HubSpot's Sensitive Data protection silently blocking activity data) and surface it. An empty or thin result under one of these isn't the same as "nothing happened" — say so rather than letting it read that way.
5. **Normalize each new result** into the common record shape in `references/schema.md` — this is what makes results from totally different tools comparable and citable, and what makes the reuse in step 3 possible on a later turn. If any two of the sources just queried are noted in the config as likely to overlap (a CRM synced with an email or call source — see `references/catalog.md`), check for likely duplicates before moving on: same type, overlapping participants, timestamps within about 15 minutes. Fold a clear duplicate into one record (keep the fuller `content_type`) and say so in the answer; when it's ambiguous, show both and flag the possible overlap rather than guessing either way.
6. **Answer with both a synthesis and the receipts**: lead with a short, direct answer to what was actually asked, then list the normalized records it was built from (source, date, participants, and either the full text or a pointer back to it), so the person can verify anything the synthesis claims rather than just trusting a summary of a summary.
7. **Before sending the answer, check it against these** (fast, not a re-derivation of the whole process):
   - Did I confirm each source's live/planned status this turn rather than assume it from memory or the catalog?
   - Did I name every `"planned"` or skipped source out loud, and check `catalog.md` for a result-time caveat on any source I did query (Nooks' seat coverage, HubSpot's Sensitive Data protection, etc.) rather than treating a thin result as "nothing there"?
   - For any `may_duplicate` pair among the sources I actually queried, did I check for overlap rather than presenting both (or neither) by default?
   - If Gong was involved, did I label its content correctly as a transcript (`api`) or a synthesized summary (`mcp`) — never the second presented as the first?
   - Does every claim in the synthesis trace back to a record actually listed in the receipts below it?

**A note on caching, since it's a natural question:** this skill re-fetches from live sources each conversation rather than keeping a persistent index across separate sessions. That's a deliberate choice, not a gap — step 3 above already avoids the most common waste (repeating a fan-out for every follow-up in one sitting), and a real cross-session cache is genuine infrastructure (a normalized local store, a refresh strategy, staleness handling) that isn't worth building without a concrete reason to. If usage ever grows to where repeated live fan-out across separate sessions is actually slow or costly, that's the point to build it, not before.

## Being useful to other skills

Another skill may need account or contact history without the person ever saying "check my communications." When that's the trigger, follow the same query process above, but skip the conversational framing: return the synthesis plus normalized records in a form the calling skill's task actually needs (inline in the response is usually enough; save to a file under `./unified-communication-output/` only if the calling context asks for a file to read separately). Document any request/response shape a specific downstream skill expects in that skill's own instructions, not here — this skill's job is to stay a general-purpose source of truth, not to know about every skill that might consult it.

**No config yet, and no person to interview?** Skip the setup interview entirely rather than blocking the calling skill on a conversation nobody can have — but don't fabricate or write a config either. For this one answer, use whatever MCP connector is actually confirmed live in the session's tool list right now (same "confirmed, not assumed" check as step 3 of the setup interview above). Never guess at an API path here: an API integration (Gong included) is a setup choice that requires asking a person which path they want and, for Gong specifically, which content type — with no person available to ask, treat anything that would need that choice as unavailable rather than assuming an answer. For Gong specifically, that means using its MCP tools if they're live (clearly labeled as a synthesis, never a transcript, same as always) and treating the API path as unavailable, not "planned." Tell the calling skill plainly which sources this answer actually drew from and that it's based on what's live in this session, not a saved setup — so if a person later talks to this skill directly, the normal interview still runs untouched; this fallback never counts as that interview having happened.

## Reference files

- `references/catalog.md` — every supported source, its current status (live pattern vs. what setup it needs), and the summary-vs-transcript note for each. Read this during setup and whenever adding a connector. Gong's entry includes the MCP-vs-API question to ask and the full API credential walkthrough.
- `references/schema.md` — the normalized record format every source's results get converted into before they're presented or handed to another skill.
- `references/gong_modes.md` — Gong API path only: account/deal/bulk/owner/content-search mode routing and each mode's step-by-step procedure. Read when a live Gong `api` query needs to decide which calls to pull.
- `references/gong_api_patterns.md` — Gong API path only: Gong + HubSpot endpoint details, auth, pagination, retries, common failure modes. Read when a Gong API call errors or when merging transcript + party data.
- `references/gong_content_search.md` — Gong API path only: content-search mode internals (match_reasons shape, metadata vs. deep search, cost tradeoffs).
- `scripts/manage_config.py` — reads and writes `~/.unified-communication/connectors.json`. Run with `--help` for usage.
- `scripts/gong_client.py` — Gong API client: list calls, search call content, fetch/merge transcripts, resolve a rep's user ID. Requires `GONG_ACCESS_KEY`/`GONG_SECRET` (see catalog.md); never has credentials embedded in it.
- `scripts/extract_gong_ids.py` — pulls Gong call IDs out of HubSpot meeting records (account/deal mode).
- `scripts/format_transcript.py` — writes fetched Gong transcripts to readable files, single or bulk-with-manifest.
